# SENTINEL — Architecture Decision Record

Each entry: context → decision → consequences. Newest first is not used; entries
are numbered and appended.

---

## D-001 — Keep the existing Vite + React + TypeScript frontend instead of Next.js

**Context.** The repository already contained a working Vite 8 / React 19 /
TypeScript / Tailwind 4 application with a Cloudflare Worker. The vision prefers
Next.js.

**Decision.** Keep Vite + React + TS. SENTINEL's rendering is a client-side
operations console; it has no SEO, server-component or edge-rendering
requirement. Rewriting to Next.js would discard working infrastructure and add
a build/runtime surface with no product benefit. The Worker remains for health
checks and static hosting; the ML backend is FastAPI, which is the correct place
for Python inference.

**Consequences.** No SSR. The app must handle API unavailability gracefully, so
it ships with an exported artifact snapshot (D-004).

---

## D-002 — Two dataset integrations, never merged

**Context.** C-MAPSS (turbofan, cycles, RUL) and AI4I 2020 (machines, tabular,
failure labels) have incompatible sensors, units and failure definitions.

**Decision.** Each dataset has its own adapter, processed dataset, model family
and UI labelling. C-MAPSS powers the fleet/RUL/anomaly/health/maintenance view.
AI4I powers supervised failure classification, failure-mode classification and
tabular explainability. No feature vector mixes the two.

**Consequences.** The platform demonstrates multi-dataset architecture without
pretending the physical systems are comparable.

---

## D-003 — Fleet assets are C-MAPSS units; AI4I is presented as its own model domain

**Context.** AI4I has no time series or machine identity suitable for a fleet
timeline (row order is not an operational history).

**Decision.** Fleet, digital twin, RUL and maintenance pages are driven by
C-MAPSS FD001 units (100 engines, run-to-failure). AI4I pages are explicitly
labelled as the "tabular failure-classification dataset".

**Consequences.** Every timeline is real telemetry. Failure probability in the
fleet is derived from the RUL model's residual distribution rather than by
applying an AI4I classifier to C-MAPSS sensors (which would be invalid).

---

## D-004 — Frontend reads the live API, falls back to an exported snapshot

**Context.** The hosted/static build cannot run Python; the demo must still show
real model output.

**Decision.** `sentinel.pipelines.build` exports `artifacts/snapshot.json` with
fleet summaries, per-asset series, metrics, EDA, registry and maintenance plan
generated from the trained artifacts. The frontend calls the FastAPI base URL
(default `http://127.0.0.1:8000/api/v1`) and falls back to that snapshot on
failure. The UI displays which data source is active.

**Consequences.** The UI is honest in both modes. Snapshot is a derived artifact,
not fabricated data.

The UI copy (`src/generated/snapshot.json`) is committed so a fresh clone can run
the console without a Python environment. It is still generated output, labelled
"Artifact snapshot" in the top bar, and is regenerated by every build; datasets
and model binaries remain git-ignored.

---

## D-005 — RUL clipping at 125 cycles and residual-based uncertainty

**Context.** C-MAPSS training trajectories are run-to-failure; RUL grows
unbounded for healthy engines, and a point estimate hides risk.

**Decision.** Clip the training target at 125 cycles (standard practice, also
used because early-life degradation is not identifiable from the sensors), and
derive uncertainty from the validation-set residual distribution. Horizon failure
risk is `P(RUL ≤ H)` using the empirical residual CDF.

**Consequences.** Predictions are capped; documented in `docs/ML_METHODOLOGY.md`.
Risk is a model-derived probability, not a certification.

---

## D-006 — Failure cost model is configurable and explicit

**Context.** Threshold optimisation and maintenance prioritisation need costs.

**Decision.** Costs live in `sentinel/config.py` (`CostModel`): false negative
(unplanned failure) 500 units, false positive 50 units, planned maintenance 120,
downtime per hour 900, etc. They are published in the UI and docs as assumptions,
not measured facts.

**Consequences.** All "savings" are scenario estimates under stated assumptions.

---

## D-007 — SQLite locally, PostgreSQL-compatible store

**Context.** No PostgreSQL server is installed on the development host.

**Decision.** SQLAlchemy models with `SENTINEL_DATABASE_URL`; default
`sqlite:///artifacts/sentinel.db`. Store holds dataset versions, model registry
entries and alert records. Switching to PostgreSQL requires only the env var.

**Consequences.** Local dev works out of the box; no Postgres-specific SQL is used.

---

## D-008 — Defer PyTorch deep learning until the environment allows it

**Context.** The dev host has ~3.5 GB free disk and Python 3.15; CUDA PyTorch is
not installed and the 4 GB RTX 3050 needs the CUDA build to be useful.

**Decision.** Implement and verify classical models first, record their metrics
as the baseline, and keep the deep-learning module `planned`. The feature and
sequence builders are already shaped for tensors (`build_sequences` returns
windowed arrays), so LSTM/GRU/CNN can be added without redesign.

**Consequences.** No false claim of deep-learning results. Baselines are in place
for a fair later comparison.

---

## D-009 — Explainability without the SHAP package

**Context.** `shap` is not installed and pulls heavy dependencies on Python 3.15.

**Decision.** Use XGBoost's exact TreeSHAP implementation
(`booster.predict(..., pred_contribs=True)`), which produces the same additive
attributions, plus scikit-learn permutation importance for non-tree models.

**Consequences.** No extra dependency; SHAP values are exact for tree models.
Linear models fall back to coefficients/permutation with a labelled note.

---

## D-010 — Anomaly severity from the healthy-data score distribution

**Context.** Unsupervised scores have no absolute scale.

**Decision.** Fit detectors on early-life ("healthy") windows of training units
and calibrate severity thresholds at the 95th/99th/99.9th percentiles of that
distribution. Severity is monotone in the score, documented and configurable.

**Consequences.** Severity is relative to a declared healthy baseline.

---

## D-011 — Live monitoring replays recorded trajectories; it does not simulate physics

**Context.** The roadmap calls for a live monitoring experience with streaming
telemetry, but the project has no plant connection, no MQTT/OPC-UA broker and no
physical simulator. Generating sensor values would violate the no-fabrication
rule and make every downstream estimate untrustworthy.

**Decision.** The build exports `artifacts/replay.parquet` — one row per recorded
C-MAPSS test cycle with the pipeline's RUL, band, horizon risk, anomaly score,
severity and health for that cycle. `WS /api/v1/ws/replay/{asset_id}` streams
those rows with pause/resume/speed/seek/restart; pacing is the only thing the
client controls. Every screen shows "Simulated replay" and states that no live
sensor connection exists.

**Consequences.** The stream is honest and reproducible, and it demonstrates the
real-time architecture without pretending to be a digital twin of physical
hardware. An MQTT/OPC-UA adapter can later replace the artifact source behind
the same message contract. RUL bands and anomaly severity are absent in the
offline artifact fallback rather than being invented.

---

## D-012 — Forecasting uses direct multi-horizon models with a per-engine chronological split

**Context.** Sensor forecasting asks for cycle `t+h` from history up to `t`, which
is a different task from RUL. Shuffling rows or using a random split would leak
later cycles into training and inflate the score.

**Decision.** For each of four C-MAPSS sensors, build causal lag/rolling/EMA
features (all windows shifted by one cycle) and predict horizons 1–10 directly.
Compare persistence, a 15-cycle moving average, exponential smoothing (α=0.3)
and HistGradientBoosting. Split chronologically *inside every engine*: first 70%
of cycles train, remaining cycles test. Report MAE, RMSE and MASE (scaled by the
naive one-step error on training rows). Trees predict the change from the current
value rather than the absolute level, because a tree cannot output values beyond
its training range and the degrading tail lies above it.

**Consequences.** Exponential smoothing wins all 12 reported sensor × horizon
cells (mean MASE 0.881) against persistence (1.061); the boosted model reaches
1.054 and is kept as an honest negative baseline. No recursive simulation or
future values are used, and the page states this explicitly.

## D-013 — Alert lifecycle state lives in the store, keyed by a stable fingerprint

**Context.** Alerts were regenerated by every build: the table was emptied and
re-inserted, so an acknowledgement would be lost and any lifecycle workflow
would be meaningless across pipeline runs.

**Decision.** Give each alert a deterministic fingerprint (`sha1(asset_id |
kind | cycle)`, truncated) and treat that as its identity. The build syncs by
fingerprint instead of deleting: new alerts are inserted as `open`, existing
ones have severity/message/score refreshed, and their `status`, actor,
timestamp and note are untouched. Open alerts the pipeline no longer produces
are deleted; acknowledged and resolved alerts are kept as an audit trail. The
store migrates old databases in place with `ALTER TABLE` additions.
Acknowledge/resolve transitions are terminal in one direction (resolved alerts
cannot be acknowledged or resolved again → HTTP 409) and record who acted and
when.

**Alternatives rejected.** Deleting on every build (loses state); keying by the
auto-increment id alone (new ids on every build); storing lifecycle in the
snapshot (mutations would be overwritten by the next export and the UI would
need a write path into a static file).

**Consequences.** The lifecycle survives rebuilds without a reset step, and the
store is the single source of truth for operational state. The UI records
`console-operator` as the actor until real identities exist; the API already
accepts any actor string, so an auth layer can supply it later.

## D-014 — Saved scenarios store the computed plan, not a budget to re-run

**Context.** Comparing maintenance budgets only works if both sides are
reproducible records. Re-optimising a saved budget after the fleet or cost model
changes would silently rewrite history and make a comparison misleading.

**Decision.** `POST /maintenance/scenarios` runs the optimiser once and persists
the complete returned plan as JSON (selection, deferred list, strategy costs,
assumptions) alongside flattened summary columns for listing and comparison.
Comparison loads those stored plans; it never recomputes them. A scenario is
immutable until deleted. Each metric marks its own best value instead of
producing one aggregate "winner", because budgets trade total avoided loss
against efficiency per dollar.

**Alternatives rejected.** Storing only the budget and recomputing on read
(comparisons drift with the fleet); serialising plans to files (no queryable
list, no delete, awkward in containers); adding scenarios to the snapshot (the
build would overwrite user-created state — the same reason alert lifecycle moved
to the store, D-013).

**Consequences.** Comparison is a reproducible audit of tested budgets. Saved
plans can become stale relative to the current fleet, so the record carries its
creation timestamp and the page labels them as saved runs rather than current
recommendations.

## D-015 — Onboarding requires an explicit mapping and a passing validation gate

**Context.** The research adapters can hardcode column names because the files
are fixed. A plant export cannot be guessed: headers are local, sensors are
partial and units are undocumented. Auto-detecting a mapping and importing
immediately would produce plausible-looking rows that silently mean something
else.

**Decision.** Onboarding is a four-step contract: inspect (suggest aliases with
confidence), map (every source column explicitly assigned or ignored), validate
(coerce, check keys/order/missingness/history and report every issue with a
severity), then import. Blocking errors refuse the import with 422; warnings
allow storage but mark the asset not score-eligible. The registry stores the
exact mapping per asset as JSON next to the canonical parquet, keyed by
canonical asset id (upsert on re-import). Scoring is a separate gate: validated,
all 21 sensors mapped, at least 30 cycles. Only then does the RUL model run, and
the response states that applying a C-MAPSS model to plant data is an
out-of-distribution check.

**Alternatives rejected.** Fuzzy auto-mapping without confirmation (ambiguous
labels such as Ps30, NRf and NRc map to two channels each); importing with
warnings suppressed (operators cannot see what was assumed); scoring any stored
asset regardless of coverage (the feature contract would silently produce NaNs
or invented defaults); storing only one global mapping (different suppliers use
different headers).

**Consequences.** Bad data cannot reach a model, and every stored row is
traceable to the mapping that produced it. The cost is operator effort: a new
header set needs review, and an export with no cycle column or fewer than 30
cycles is stored but cannot be scored.

## D-016 — Profiles store the expected schema, and drift must be acknowledged

**Context.** A saved mapping is only reusable if the next export still has the
columns it was built from. Vendors rename headers, add fields and occasionally
drop one. Applying the old mapping silently would either fail validation later
or, worse, attach a canonical field to different source data.

**Decision.** A mapping profile stores the exact mapping and the ordered column
set at save time. Every reuse compares the profile schema with the incoming file:
added columns are reported and left unmapped (with suggestions); renamed columns
are matched by normalised name or ≥ 0.8 string similarity, the mapping follows
the new name, and the import requires `accept_drift: true`; missing mapped
columns block the import until accepted, at which point their canonical targets
are dropped. Accepting drift refreshes the profile's mapping and expected
columns, so the next export is compared with the accepted baseline. Validation
and the apply endpoint return the same drift report without writing anything.

**Alternatives rejected.** Exact header equality (too brittle for real exports);
fuzzy auto-apply without acknowledgement (a rename can silently move a sensor to
a different canonical field); treating missing mapped columns as warnings
(silently reduces what the asset measures); storing only the mapping and no
expected schema (no way to detect drift at all).

**Consequences.** Repeated imports are one click plus a review when something
changed, and the review is recorded in the response and in the asset's quality
report. The cost is that a genuinely renamed column with no name similarity is
treated as missing + added and needs manual mapping; profile baseline history is
not retained, only the current expected schema.

## D-017 — Partial-sensor assets get their own baseline and a relative health signal

**Context.** The onboarding gate required all 21 C-MAPSS sensors before an asset
could be scored. Most real exports map a handful of channels, so those assets
were registered but operationally silent — no health, no alert, nothing in the
console. Imputing 21 sensors or borrowing a fleet baseline would fabricate data.

**Decision.** At import, each asset learns a baseline from its first 10–30 cycles
(or 30% of its history): per mapped sensor, robust median, MAD-derived scale and
natural slope over cycle. Health compares the latest cycle with that detrended
baseline, averages the largest robust z-scores, adds a short-term worsening-trend
penalty and publishes an explicit coverage/confidence level. One sensor with 10
cycles is the technical minimum, three sensors with 20 cycles the recommended
minimum for a usable signal, six or more sensors high confidence. Usable
warning/critical assessments create `plant_health` alerts with source `plant`;
C-MAPSS alert synchronisation is scoped to source `cmapss` and cannot prune them.
The 21-sensor RUL score stays an unchanged, explicit opt-in.

**Alternatives rejected.** Requiring all 21 sensors (silent assets); imputing
missing channels (invented data); one fleet baseline (different units and
operating points); showing a score without coverage (false confidence); lowering
the RUL sensor gate (out-of-distribution model contract).

**Consequences.** Partial exports become operationally visible and alerting works
from the first usable export. The health number is relative to the asset's own
baseline and is not a remaining-life estimate; a baseline captured during a fault
normalises that fault, and plant alerts persist until an operator resolves them.

## D-018 — Host on App Service + Static Web Apps + PostgreSQL Flexible Server

**Context.** The platform needed public hosts on an Azure for Students
subscription. The console is a static Vite build; the API is Python with
scientific wheels; Container Registry Tasks are blocked for this subscription,
so a Docker/ACR path could not build images in Azure.

**Decision.** Run FastAPI directly on App Service Linux (Python 3.15, B1),
serve the console from Static Web Apps Free, and use PostgreSQL Flexible Server
(B1ms) for the operational store. Deploy the API as an Oryx zip build and start
it with `startup.sh`; build the console locally with
`VITE_API_BASE_URL=https://sentinel-api-l1fit9.azurewebsites.net/api/v1`.
CORS allows only the Static Web App origin (plus loopback development origins).
The SQLite registry is copied into Postgres idempotently at startup.

**Alternatives rejected.** Docker + ACR (Tasks not permitted on the student
subscription); Render/Neon (the user chose Azure); App Service with a managed
Python build only (the extracted Oryx output references a temporary virtualenv
path, so startup uses the runtime interpreter with the extracted site-packages);
bundling the frontend into the API container (unnecessary and slower).

**Consequences.** The API is a single B1 instance with one uvicorn worker, so a
cold start and the first database connection take several seconds; the client
allows 12 s. The schema is initialized once at startup rather than per request.
Deleting `output.tar.zst` while `oryx-manifest.toml` still says the output is
compressed breaks every restart; the manifest must be removed after manual
extraction. Hosts and settings are recorded in `docs/DEPLOYMENT.md`.
